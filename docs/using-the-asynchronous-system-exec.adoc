= Using the Asynchronous System Exec
:imagesdir: ./img/

Welcome to the docs on how to use the Asynchronous System Exec library. Let's dive in!

== Library Overview

The Asynchronous System Exec API consists of two classes; 

* `serenial.io-ase.lvlib:ase.lvclass` contains the main component of the library. 
* `serenial.io-ase.lvlib:configuration.lvclass` provides an interface to configure some of the advanced features of the library whist allowing for future expansion without breaking changes.

The API VIs are located in the `API` folder of the `ase` class. Usage information for each VI is available via the context help.

_PING.exe_ will self-terminate after performing the specified _five_ ping-operations of IP address `127.0.0.1` so the only other VI that must be called is `Conclude Call.vi`; This will wait for the `ping` executable to finish, clean up any internal resources and return the executable's exit code.

.Please note the following;
*  Not all executables will self-terminate! You might have to either send the termination signal using `Send Terminate.vi` or indicate via some other method, perhaps writing to or closing the Standard Input, that you want the executable to finish and exit.
* The `ASE Handle` inputs and outputs for library calls is _by-reference_ i.e. you perform operations on the instance pointed to by the handle. This means that the `ASE Handle` wire can be branched without creating copies of the instance.
* If the executable we need to call is not in the system's PATH environmental-variable, the absolute path to it can also be used. Simply wire a LabVIEW `Path` type into the executable name terminal.
* If no Event References are passed to `Start Call.vi` then any data on the Standard Output or Standard Error is safely and silently discarded.

_and finally_

WARNING: You must ensure that `Conclude Call.vi` is used when you have finished with the Asynchronous System Exec instance to ensure all internal resources are de-allocated.

== The Flexibility of Asynchronicity
You might be thinking - _Huh, you said the library was asynchronous but we still have to wait at `Conclude Call.vi`?_ - Well, yes! That is true so lets see what else we can do.

The `Wait on Call.vi` allows for us to wait for the executable to exit but with a timeout specified in `milliseconds`. The VI is non-blocking so multiple calls to `Wait on Call.vi` will execute simultaneously. 

In fact, `Wait on Call.vi` and `Conclude Call.vi` will not block _any_ API calls so we can be flexible in how we structure our applications. This is illustrated with the example below;

[#img-wait-on-call]
.Using the Wait-on-Call feature
image::using-wait-on-call.png[An example of using Wait-on-Call VI]
{empty} +

.What will happen when we run this example?
. `Start Call.vi` launches the _Windows Command Prompt_ asynchronously. 
. The execution will then split along three asynchronous branches `A`,`B` and `C`.
. Branches `A` and `B` will wait on `Conclude Call.vi` and `Wait on Call.vi` respectively.
. The `Wait on Call.vi` on branch `C` will wait for `200ms` then `Write to StdIn.vi` followed by `Send Terminate.vi` will be called, the latter triggering the _Command Prompt_ executable to exit.
. After the _Command Prompt_ has exited, `Conclude Call.vi` and `Wait on Call.vi` of branches `A` and `B` will complete and everything will resynchronize at the `Merge Errors`node.

== Using the Advanced Configuration
The `configuration.lvclass` provided with the library allows for the advanced configuration features to be utilized.

One, many or all of the features can be implemented at once depending on what `configuration.lvclass` methods are overridden.

_Currently these features are;_

*Specification of an Event Identifier String*

This identifier string is provided with each event allowing for the originator of an event to be easily identified when multiple Asynchronous System Exec events share the same Event References and Event Case Structure.

*Custom Event Stream Split Character-Match Regular Expression*

By default, the Standard Output and Standard Error streams are split on a `newline` character (`\n`) but this behavior can be changed to any valid https://www.boost.org/doc/libs/1_77_0/libs/regex/doc/html/boost_regex/syntax/perl_syntax.html[`PERL` regular expression]. For example, the expression `[0-9]` would split the stream on any numeric character.

Create a child class of `serenial.io-ase.lvlib:configuration.lvclass` which overrides `Stream Split Character Match RegExp Std Out.vi` and/or `Stream Split Character Match RegExp Std Error.vi` to use this feature.
